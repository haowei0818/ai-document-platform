# AI 文件管理平台：LLM 整合層工程化 — 任務卡（Tickets）

建立日期：2026-11-08
來源：/grill-me 共識（Q1～Q9）
實作環境：Claude Code（家裡電腦 WSL2）
硬性限制：**全程零成本**，只用 Gemini 免費額度，不引入付費服務或 Redis 這類新元件

## 執行順序總覽

```
T0 查證
 └─ T1 測試不花錢、不留垃圾（地基）
     ├─ T2 刪除文件不殘留向量 ──┐
     ├─ T4 暫時性錯誤自動重試 ─┐ │
     └─ T8 真實整合測試（選用）│ │
                              │ └─ T3 上傳處理狀態 ── T5 手動重新處理 API
                              ├─ T6 問答失敗回 503
                              └─ T7 LLM 呼叫可觀察
 全部完成 → T9 文件與履歷更新
```

- **可以平行做的**：T2、T4、T8（都只依賴 T1）；T6、T7（都只依賴 T4）
- **建議的單人實作順序**：T0 → T1 → T2 → T3 → T4 → T5 → T6 → T7 → T8 → T9
- 每張卡完成後：測試全綠 → `git status` 確認 → commit → push → 整理學習筆記

## 跨卡共用的不變條件（Invariants）

這幾條規則在每張卡完成後都必須成立：

1. **Chroma 裡只會有 `ready` 文件的 chunk。** 處理中（`pending`）的文件會先清掉舊 chunk 才開始重建；處理失敗（`failed`）時會清掉寫到一半的資料。所以問答時不需要另外判斷狀態，現有的 `user_id` 篩選就夠了。
2. **所有 LLM 呼叫都必須經過 LLM Service。** 除了 Service 本身，其他模組都不能直接 import Gemini SDK。
3. **所有向量的寫入和刪除，都以 `document_id` 為單位，並集中在同一個模組。**
4. **預設的測試不打網路、不需要 API key、不寫硬碟上的 Chroma。**
5. **log 和 API 回應都不能包含 prompt、文件內容或內部錯誤細節。**

## T1｜測試不花錢、不留垃圾（LLM Service 和 Chroma 依賴抽換）

- **使用者價值**：任何人 clone 下來，不需要 API key、不需要網路就能跑完全部測試，而且不消耗額度、不留下垃圾資料
- **範圍**：
  - 新增 LLM Service 深模組，對外只有兩個能力：
    - `embed`：文字轉成向量
    - `generate`：根據 prompt 生成回答
  - 模型名稱、API key、SDK 用法全部封裝在 Service 裡面
  - `rag_utils` 和 `DocumentAskView` 改成透過 Service 呼叫 LLM
  - 「取得 Chroma collection」改成可以替換的依賴：
    - 正式環境用硬碟（`./chroma_db`）
    - 測試用記憶體模式
  - 每個測試使用獨立的 collection（或在測試前重置），避免測試之間互相污染
  - 既有測試改成 mock LLM Service
  - 移除 `chroma_db_test/`；評估 `settings.TESTING` 的路徑切換邏輯能不能簡化或移除
- **驗收條件**：
  - [ ] 拔掉網路、移除 API key 的情況下，原有的 18 個測試全部通過
  - [ ] 跑測試後，專案裡不會產生 `chroma_db_test/` 或任何 Chroma 檔案
  - [ ] 連續跑兩次測試，結果完全相同（deterministic）
  - [ ] 單獨跑任一個測試、或打亂順序跑，結果都相同（證明測試互相隔離）
  - [ ] 用 grep 搜尋，Gemini SDK 只出現在 LLM Service 裡
  - [ ] 對外 API 行為不變（這是純重構，不改功能）
- **相依**：T0

## T2｜刪除文件不殘留向量

- **使用者價值**：文件刪除後，它的內容絕對不會再出現在問答結果裡（修補資料殘留的安全問題）
- **範圍**：
  - 建立「依 `document_id` 刪除全部 chunk」的單一入口，之後 T3、T5 會重複使用
  - 刪除文件的 API 同步刪除對應的向量
- **驗收條件**：
  - [ ] 刪除後，Chroma 裡找不到任何屬於該 `document_id` 的 chunk
  - [ ] 刪除後問相關問題，`sources` 不會出現該文件
  - [ ] 只刪除目標文件的向量，同一使用者的其他文件和其他使用者的資料都不受影響
  - [ ] 刪除一份 Chroma 裡本來就沒有向量的文件（例如處理失敗的文件），不會報錯
- **相依**：T1
- **備註**：如果 T0 查證發現原本就有漏洞，這張卡完成後可以寫進履歷：「發現並修補文件刪除後向量殘留的資料外洩風險」

## T3｜上傳處理狀態（`pending` / `ready` / `failed`）

- **使用者價值**：上傳後可以看到文件是否真的可以拿來問答；系統不會再出現「顯示上傳成功、其實問不到」的情況
- **範圍**：
  - `Document` 新增狀態欄位，包含 migration（資料庫結構變更檔）
  - 上傳後的流程：先存成 `pending` → 先清掉舊 chunk → 處理
    - 處理成功：改成 `ready`
    - 處理失敗：清掉寫到一半的 chunk，改成 `failed`
  - 文件列表和上傳回應都顯示狀態；狀態是唯讀的，不能由使用者寫入（防 mass assignment）
  - 上傳時 LLM 失敗不算上傳失敗：仍然回傳成功的狀態碼，但 `status` 是 `failed`
- **驗收條件**：
  - [ ] 正常上傳後狀態是 `ready`
  - [ ] mock LLM 失敗時，狀態是 `failed`，文件仍然保留，Chroma 裡沒有殘留的 chunk
  - [ ] mock 處理到一半才失敗（前幾段成功、後面失敗），Chroma 裡仍然沒有殘留
  - [ ] `failed` 文件的內容不會出現在問答結果裡
  - [ ] 使用者在上傳時夾帶 `status` 欄位，不會被寫入
  - [ ] 既有的舊文件在 migration 後狀態是 `ready`
- **相依**：T1、T2

## T4｜暫時性錯誤自動重試

- **使用者價值**：網路抖一下、瞬間撞到流量限制時，系統自己就恢復了，使用者感覺不到
- **範圍**（全部封裝在 LLM Service 裡，呼叫端不需要修改）：
  - 錯誤分類：
    - **暫時性錯誤**（要重試）：`429` 流量限制、逾時、連線錯誤、Gemini 端的 5xx 錯誤
    - **持續性錯誤**（不重試）：每日額度用完、認證錯誤、請求格式錯誤
  - 最多重試 3 次，每次等待時間拉長（指數退避）
  - 用盡重試次數或遇到持續性錯誤時，拋出 Service 自己定義的統一例外（給 T3、T6 接）
  - 等待機制要可以替換，讓測試不需要真的等待
- **驗收條件**：
  - [ ] mock「失敗 2 次後成功」：最後成功，總共呼叫 3 次
  - [ ] mock「一直暫時性失敗」：在第 3 次重試後拋出統一例外
  - [ ] mock「持續性錯誤」：只呼叫 1 次就拋出例外，不重試
  - [ ] 測試執行時間不受退避等待影響（不會真的 sleep）
  - [ ] 呼叫端看不到任何 Gemini SDK 的原生例外
- **相依**：T1

## T5｜手動重新處理 API

- **使用者價值**：處理失敗的文件（例如當天額度用完）隔天可以一鍵重跑，不需要刪掉重傳
- **範圍**：
  - 新增「對單一文件重新執行 RAG 處理」的 API（建議使用 `POST`，路由帶文件 `pk`）
  - 流程跟 T3 相同：改成 `pending` → 先清舊 chunk → 處理 → 改成 `ready` 或 `failed`
  - 權限：必須登入；只能操作自己的文件
- **驗收條件**：
  - [ ] `failed` 文件重新處理成功後變成 `ready`，可以問答
  - [ ] 對 `ready` 文件連續重新處理兩次，chunk 數量和第一次處理完全相同（冪等）
  - [ ] 未登入回 `401`
  - [ ] 操作別人的文件回 `404`（不透露文件是否存在）
  - [ ] 重新處理失敗時狀態變成 `failed`，沒有殘留的 chunk
- **相依**：T3

## T6｜問答時 LLM 失敗回 503

- **使用者價值**：AI 服務暫時不能用時，使用者收到清楚的「請稍後再試」，而不是一堆錯誤頁面或內部錯誤訊息
- **範圍**：
  - 問答流程中，不管是向量化還是生成階段失敗，都回 `503`
  - 統一錯誤格式：錯誤代碼（例如 `llm_unavailable`）加上一句友善說明
  - 內部錯誤細節只寫進 log
- **驗收條件**：
  - [ ] mock 向量化階段失敗：回 `503`，格式正確
  - [ ] mock 生成階段失敗：回 `503`，格式正確
  - [ ] 回應內容不包含例外訊息、API key、模型名稱或堆疊追蹤（stack trace）
  - [ ] 錯誤有被記錄到 log
  - [ ] 正常問答的回應格式維持 `answer` 和 `sources`，不受影響
- **相依**：T4

## T7｜LLM 呼叫可觀察（結構化 log）

- **使用者價值**：開發者可以掌握每次 AI 呼叫的耗時、token 用量、失敗率，知道離免費額度上限還有多遠
- **範圍**（全部在 LLM Service 內完成）：
  - 每次呼叫輸出一筆結構化 log，欄位包含：
    - 操作類型（`embed` 或 `generate`）
    - 模型名稱
    - 耗時
    - 成功或失敗
    - 重試次數
    - token 用量（Gemini 有回傳時才記錄）
  - 使用 Python 內建的 `logging`
- **驗收條件**：
  - [ ] 成功的呼叫會產生一筆 log，包含上面所有欄位
  - [ ] 失敗的呼叫也會產生 log，並且能看出重試次數
  - [ ] log 裡**不能**出現 prompt、問題或文件內容（測試要拿一段特殊字串檢查，確認它沒有出現在 log 裡）
  - [ ] Gemini 沒有回傳 token 用量時，log 仍然正常輸出，不會報錯
- **相依**：T4

## T8｜真實整合測試（預設不執行）

- **使用者價值**：能在免費額度內偶爾確認「mock 和現實沒有脫節」，例如 Gemini 改格式或模型下架時可以發現
- **範圍**：
  - 1～2 個打真實 Gemini 的測試，分別驗證 `embed` 和 `generate` 的回傳格式
  - 只有設定特定環境變數時才執行，預設會被跳過（skip）
- **驗收條件**：
  - [ ] 預設跑測試時，這些測試顯示為「已跳過」，而且不打網路
  - [ ] 設定環境變數並提供 API key 後，測試能真的呼叫 Gemini 並通過
  - [ ] 單次執行消耗的請求數在 5 次以內
- **相依**：T1
